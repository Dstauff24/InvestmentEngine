# CLAUDE.md — Investment Decision Engine (Rebuild, Oct 2026)

## What this is
A personal investment decision-support engine for a Schwab brokerage account. **TWO LAYERS, and the first one is the product (D52).**

**The CORE layer — portfolio discipline — is the primary deliverable**: allocation against target, drift, fund quality, concentration, and opportunity-cost reviews. It earns its keep without predicting anything, because it enforces decisions already made. It is never put at risk by the sleeve, and **capital flows INTO core and never back out** — no rebalance, sweep or top-up may move capital from core into growth, at any drawdown.

**The GROWTH sleeve is the experiment.** It ingests quant + qual data, scores tickers through a 4-pillar confluence model, surfaces complete trade plans (entry/stop/TP1/TP2/R:R/size) in two tiers, tracks every idea in a Shadow Book, and sends a daily digest. It runs on D40's ladder, and **it has a stopping rule (D51)**: six months from the first lab-derived strategy entering shadow, the sleeve must show >=30 closed Shadow Book calls at >=+0.05R live expectancy, or it is SHELVED and the engine runs as the core layer alone. The date the clock starts goes in the decision log on the day it happens, or the rule has no start.

**The human makes every final decision.** No UI in Phase 1; read-only broker access, no order placement anywhere.

## Non-negotiable process rule (D30)
**Commit and push to GitHub at the end of every working session, and after every completed step. No exceptions.** The repo on GitHub is the system of record; a Codespace is disposable. Never report a step complete without naming the commit that was pushed.

**Deploying is `./scripts/deploy.sh` on the engine host** — pull, dependencies, `db.init` (migrations then schema), config validation, then the orchestrator's own `--dry-run` preflight. It makes NO provider calls and writes no market data (no `ALLOW_LIVE_CALLS` anywhere in it, pinned by a test): a deploy that ingested would merge "did the deploy work" with "did tonight's data arrive", which have different answers and different fixes. Exit code is the hard-error count; a preflight SKIP is a known state, not a failure. The one-time deep-history catch-up is a separate, ordered runbook in README.md — actions BEFORE bars, basis repair after, `price_basis_check` to prove it.

## Evidence must be reproducible (from Oct 22 2026)
**Every backtest records the commit, a hash of the EFFECTIVE config, and a dirty-tree flag — on every CSV row and in the report header.** A dirty tree REFUSES to run; `--allow-dirty` runs anyway and stamps the output `baseline=False` for ever, a diagnostic and never evidence. A repository that cannot be read counts as dirty, because the rule is "prove the tree is clean" and an unanswerable question is not a yes. The report says **MIXED CODE** when rows span two commits (the difference between the arms is then partly the code, so it is not a comparison) and warns when two arms share a config hash (the override changed nothing, so the difference is sampling).

**ANY DECISION THAT ADOPTS A VALUE OR A MODE CITES THE EVIDENCE RUN'S COMMIT AND CONFIG HASH** in its decision-log entry. "The backtest said +0.68R" is not checkable; "+0.68R on `39ed4e3` / config `944f268531bc`" is — anyone can check out that commit, load that config, and get the number back. This exists because three runs in one afternoon were invalidated by edits landing mid-walk, and each time the only thing that caught it was remembering.

Quarterly one-way ratchet sweeps half of any excess above 3 points into Core permanently; drawdowns are never replenished mid-quarter.
- **Abstention semantics (D41):** a pillar with insufficient data ABSTAINS; the composite is computed over SCORING pillars with weights RENORMALIZED (never scored 50 — that invents evidence). An abstainer can neither agree nor conflict, so D12's counts bind on scored pillars (**a two-pillar idea reaches at most Tier B**) and the conflict cap applies only to scored pillars. **Technical must have scored or there is no idea** — it carries 40 points and is never genuinely unavailable for a liquid listed name, so its absence means the data is wrong. The abstention mask is printed on every card and recorded on every Shadow Book row (`scored_pillars`, `pillars_scored`), because 72 from four pillars and 72 from two are different claims and the number cannot say which; D39 groups calibration on it.
- **The mapping (`scoring/pillars.py`):** one shape everywhere — `50 + 50 × clamp(x / full_credit, −1, +1)`, neutral at 50, SATURATING at ±full_credit so one wild sub-signal cannot dominate a pillar. A pillar is the MEAN of the sub-signals that scored, i.e. D41's renormalization one level down. **Equal sub-weights within a pillar is a decision, not a missing parameter**: D2/D32 state the weights between pillars; nothing states whether revision momentum outranks margin trend, so a number there would be false precision. ATR is deliberately unscored (a risk unit, not an opinion). Beyond its horizon a catalyst scores `None`, not 0 — no news is not bad news.
- **Two phases (`scoring/runner.py`):** phase one scores every symbol, phase two ranks percentiles and tiers. Forced by D33 — a percentile cannot be known until every symbol is scored. Sector composites are built ONCE per run and cached (11 builds, 422 hits on the live 433-symbol universe).

- **Shadow Book (D13):** every surfaced idea (Tier A, Tier B, and discretionary) logged with projections at time of call, tracked to outcome whether or not taken. `shadow_book.symbol` has NO FK to `tickers` (discretionary ideas may be off-universe). North-star metric = expectancy per recipe and tier.
- **The tracker reads bars in the CALL's price basis.** `shadow_book` stores absolute levels frozen at the call (D13) and `prices_daily` is raw (D24), so a 10-for-1 split while a trade is open makes every later bar print a tenth of the plan's units — compared straight, the first post-split bar is a 90% collapse and the tracker books a stop-out the market never inflicted, then that row counts as closed evidence under D40's ladder. A reverse split books TP2 the same way. `outcome_tracker.in_call_basis` rebases the BARS (and dividend amounts, or D19(2)'s stop adjustment lands in the wrong units) FORWARD from the call — the mirror of D24's back-adjustment from today — because the projections must not be rewritten. `backtest/resolve.py` was already correct (it prefers `adj_*`), and a named test allowlists the only three modules that may read raw bars, each with its reason.
- **Projections are frozen; the enforced stop is not.** `shadow_book` carries `proj_stop` (what we said at the call, never written again) beside `current_stop` (what the tracker enforces, moved to breakeven at TP1 per the trim rules, lowered by a dividend per D19(2)). A projection that drifted toward the outcome would measure nothing, which is the entire point of D13.
- **The ambiguous bar resolves PESSIMISTICALLY.** Daily bars carry no intrabar sequence, so a bar touching both stop and target is unresolvable — and the cost is asymmetric: assuming the target came first flatters every result in exactly the case where a real trade was most likely stopped out. `shadow_book/outcome_tracker.py` books the stop, unless the stop is already at breakeven, where TP1 was already paid. `last_evaluated_on` is what makes the daily job safe to re-run.
- **The backtest and the Shadow Book share ONE fill implementation.** `backtest/resolve.py` builds the call dict and hands it to `shadow_book.outcome_tracker.evaluate_call`; it re-decides nothing. The entry-zone fill, the pessimistic ambiguous bar, the breakeven move at TP1 and the D19(2) dividend stop are modelling CHOICES, and a backtest that scored them differently would report an expectancy the Shadow Book could never reproduce — two numbers disagreeing for ever with no way to say which was the strategy.
- **What a backtest here can and cannot measure (D39(4)/O7).** It measures the RECIPES. It does not measure the composite, the tier gates or D33's ranking: the fundamental statements reach back five years but the estimate-revision, IV-rank, insider and news series all start 2026-10-21, so a historical composite would be a two-pillar number dressed as a four-pillar one. **No portfolio queue** — every signal is taken, because D17's heat cap and D38's sector guard would measure which signal arrived when a slot was free rather than what the recipe is worth. **One open trade per symbol per recipe**, or a setup that persists for a week counts its single outcome five times. **Survivorship is unfixable here**: the universe is today's constituents, so every delisted loser is absent and every number is an upper bound.
- **Next-day entry, and friction is charged (D39(4)).** A plan is formed on the close of the bar that produced it, so the first bar it can trade against is the next one — filling on the signal bar is the most common way a backtest invents an edge. `backtest/costs.py` charges slippage adversely on both sides and reports gross and net R side by side, because a strategy whose edge disappears into the spread never had one. - **Expectancy, not hit rate (D13).** 35% at +3R beats 70% at +0.5R, and a report led by hit rate ranks them backwards. - **THE REGISTERED DIRECTION REACHES THE VERDICT COLUMN, AND A CONTRADICTION SAYS SO (O23).** The lab's spread is `top quintile OF THE MEASURABLE minus bottom`, carrying no notion of good or bad — so a `lower_is_better` hypothesis is CONFIRMED by a NEGATIVE spread (`expected_spread_sign`, written down once because it is easy to get backwards). `direction` was validated at registration and then ignored by the report, so a cell pointing the opposite way to its hypothesis printed "survives both bars": `low_volatility` measured **+12.52% at 120 sessions**, which is HIGH volatility outearning low, and read as a confirmed low-volatility premium. It now prints **CONTRADICTS its registered direction**; an `unsigned` hypothesis can never contradict (nothing was pre-committed, so either sign is a finding) and an INSIGNIFICANT result never contradicts however it points, because a null is no evidence rather than evidence against. **The BH and Bonferroni arithmetic is untouched by direction** — both are procedures over two-sided p-values and `m`, and making them one-sided after the fact would move the bar to suit the answer — so a contradiction still counts as a detected effect and what changes is whose effect the line says it is.
- **THE POSITIVE CONTROL IS THE DRIFT EVENT STUDY, NOT MOMENTUM (O23).** A control has to be an effect the harness would CERTAINLY see if it worked. `momentum_12_1` measured null in all nine cells over 2008-2026 (|t(NW)| <= 0.86) and that null is **CONFOUNDED, so it convicts nothing**: the 2009 momentum crash sits inside the window, large-cap momentum has been weak since, and O22's survivorship removes the delisted losers the short leg needs. `earnings_surprise_magnitude` takes the job — forward returns after verified-beat reports by surprise quintile, on D49's point-in-time rules — because it is the one effect the engine has CERTIFIED in-house (D48, +0.22R out of sample). **A null there puts the HARNESS under suspicion rather than the market.** Pre-registered and not yet run: the event-study engine does not exist. **ITS CAVEAT IS PRE-REGISTERED TOO**: surprise is cut on VENDOR estimates, which get revised after the fact (D48 holds one with `lastUpdated` sixteen months after its report), so **on failure estimate revision is checked before the harness is blamed** — restrict to events whose estimate rows show no `lastUpdated` after the report date and measure again — and **on success the same caveat bounds the MAGNITUDE**, which then says the effect is detectable and not how large it is. Both branches committed in advance, because a control that decides how far every null can be trusted must not have its excuse invented afterwards.
- **THE `unknown` REGIME CELL IS THE WORST ONE IN THE REPORT, AND NOW CARRIES O22's LABEL.** D45 cannot compute a regime until the benchmark has 200 sessions, which over the deep window means the earliest dates — the 2008-09 crisis itself, at the thinnest coverage in the table (~343 against a median of 397) and the most extreme spread in it. Keying the survivorship flag on bear-regime NAMES left it bare and inverted the mechanism's intent, which is to mark where the bias is worst.
- **A HYPOTHESIS THIS WINDOW CANNOT CONFIRM SAYS SO ON EVERY ROW (`confirmation_withheld`).** Non-empty marks a measurement admissible as a REFUSAL and never as support, printed as `<< CANNOT CONFIRM HERE` on each of that hypothesis's rows plus a footnote carrying the reason — on every row rather than once underneath, because a verdict read on its own line is exactly how "survives" came to stand in for a contradiction. The text lives in the REGISTRY, not the renderer, because it is part of the pre-registration.
- **AN EXTERNALLY MOTIVATED HYPOTHESIS IS NOT A SIGN FLIP, AND IT STILL CANNOT BE CONFIRMED HERE (O23).** `short_term_reversal` (prior 20-session return, `lower_is_better`, Jegadeesh 1990 / Lehmann 1990) was registered the day `rsi_reset` and `relative_strength_vs_sector` both came back pointing at short-term losers. Re-registering THOSE with the sign turned round would be choosing a sign after seeing a spread; taking the horizon and direction from the literature is not. **But a hypothesis registered the day after a related result is still suggested by it, so this window can only REFUSE it** — confirmation comes from the forward `daily_candidates` record (D42), written before anybody looked. Adding it moved **m from 54 to 63 and tightened Bonferroni from 0.00093 to 0.000794**: a new hypothesis makes every other one's bar harder, which is the cost of breadth and the reason `m` comes from the registry.
- **[OPEN] parameters (D25):** every number no decision fixes lives in config tagged `# [OPEN]`, with a row in `docs/open-parameters.md` and a sync test. Changing a decision-fixed value without a decision fails a named test.

## Validated API findings (do not rediscover these)
**FMP `/stable/`:** quote at `/stable/quote?symbol=X`; `calendarYear` is now `fiscalYear` (accept both); fundamentals cost 5 calls/symbol, refreshed on staleness (>7 days or reported since), not schedule; estimates must drop already-reported periods before diffing.
- **The EOD `full` endpoint is SPLIT-ADJUSTED, and the RAW one is named as though it were the opposite.** `/stable/historical-price-eod/full` returns a `close` already adjusted for every later split — verified 2026-10-21, LRCX's 10-for-1 on 2024-10-03 shows no price jump at all. Raw bars (what D24 stores) are on `/stable/historical-price-eod/non-split-adjusted`, whose fields are `adjOpen`/`adjHigh`/`adjLow`/`adjClose` with **no `close` key**, and those `adj*` values are the UNADJUSTED prices. Trusting the field names gets it backwards in both directions. Volume on the `full` endpoint is split-adjusted too, which is harmless for a 20-day average and wrong for anything stored.
- **AND `non-split-adjusted` IS THE ADJUSTED FEED WITH THE SPLIT LOG REVERSED BACK OUT — it is not an independent raw series.** Measured over the O19 backfill (18 years, 434 symbols): **166 of 167 unambiguous splits step in the stored bars by exactly their logged ratio and none is flat**, so where FMP's log is right the reversal is right and D24's read-time adjustment is sound. Where the log is WRONG, the "raw" price is wrong in the OPPOSITE direction and by the same factor, which is how WY's 2010-07-19 close comes back as $83.66 against a true ~$41.83: FMP logged the REIT conversion (a $26.42 special dividend ~90% in stock) as a plain 2:1 split, so a step that was really 5.2484 had a 2.0 reversed out of it. Its own adjusted series divides that pre-period by exactly 2.0 and STILL leaves a 2.62x cliff. **So a mis-logged action cannot be fixed by re-sourcing from either endpoint** — there is no uncontaminated series to fetch — which is why D57 refuses the era instead of repairing it.
- **FIELD NAMES MOVE AND NOTHING FAILS. `scripts/field_probe.py` is the only thing that notices.** It compares LIVE payload keys against the fields each parser reads, with a registry whose entries may be alternatives (mirroring `_first(row, "new", "old")`), and three static tests keep the registry honest. Measured 2026-10-22: `/stable/analyst-estimates` renamed every field we read (`estimatedEpsAvg` -> `epsAvg`, `numberAnalystsEstimatedEps` -> `numAnalystsEps`, …) and `returnOnEquity` MOVED from `/stable/ratios` to `/stable/key-metrics`. Both wrote NULLs for days under green job logs. A fixture cannot catch this: it proves the parser handles a shape it was SHOWN, never that the provider still sends it. **Run the live probe after any plan change and whenever a column looks empty.**
- **A row that parses to None still INSERTs.** `require_value_coverage` (`ingest/runner.py`) fails a writer whose parsed rows carry none of the fields that make them worth storing — the column-level twin of `for_each_symbol`'s refusal to report "ok, 0 rows". Both exist because the engine runs unattended and a green log is the only thing anyone sees.
- **Nothing may be defined below a module's `if __name__ == "__main__"` guard.** An import runs the whole body and sees it; the CLI calls `main()` first and never reaches it. One misplaced helper made every unit test pass while `python -m ingest.fmp_estimates` died with NameError on all 433 symbols. Pinned by a static test over every module.
- **EVERY CALENDAR ENDPOINT IS CAPPED AT 4,000 ROWS AND TRUNCATES SILENTLY.** Measured 2026-10-21: a 7-day window returned 1,823 rows, and both a 14-day and a 30-day window returned exactly 4,000 — covering an arbitrary slice of the days requested (the 30-day ask came back as 11 days from the MIDDLE). Over the 190-day window the events job uses, `earnings-calendar` returned the last 48 days and dropped every past earnings date: 76 rows for 433 symbols, none in the past. That, not `events.backward_days`, is why `post_earnings_drift` could not fire and `pullback_to_trend` refused every symbol for an unverifiable earnings exclusion. The radar now reads **`/stable/earnings?symbol=X`, one call per symbol, no cap** (`refresh_symbol_earnings`, 433 calls/day — the cost is the point), and `FMPClient._calendar` raises `FMPTruncatedResponse` on any response at the cap. A 90-day calendar window also 402s while a 30-day one answers, so a 402 there means "window too wide", not "plan".
- **No FMP endpoint publishes a release TIME.** Verified 2026-10-22: neither `/stable/earnings` nor `/stable/earnings-calendar` returns a `time` field, so every stored earnings row is `unknown` and the engine cannot tell a pre-open report from an after-close one. **Finnhub's `/calendar/earnings` carries `hour`** (`bmo`/`amc`/`dmh`) and `ingest/finnhub_earnings.py` stamps it onto rows we already hold, matched on (symbol, event_date) — never inserting, because FMP owns what an earnings row IS (D47) and two providers inserting dates would leave nothing to arbitrate. Live coverage: 15% of calendar rows carry an hour over a 90-day window (55% over the next week), and **only 56% of them match a stored FMP date** — the two providers date the same report ONE DAY apart for a large fraction of symbols (ADI 11-23 vs 11-24, CRM 12-01 vs 12-02, CIEN 12-09 vs 12-10), which is itself the argument for a reaction WINDOW rather than a single-bar gap.
- The per-symbol earnings payload and the calendar now use the SAME names (`epsActual`/`revenueActual`); the calendar's old `eps`/`revenue` are read as fallbacks. Two parsers remain, deliberately: reading one shape with the other's names yields rows that parse cleanly and carry nothing.
**Schwab (schwab-py 1.5.x, live-validated 2026-09-03):**
- **SCHWAB'S DAILY CANDLES ARE SPLIT-ADJUSTED, so it RESTATES its own history.** Verified 2026-10-21: all 14 splits inside the stored window showed no price jump in Schwab's bars, BKNG's 25-for-1 included. D24 defines `prices_daily` as raw and applies split factors at READ time, so a stored Schwab bar from before a split gets adjusted twice. **It was dormant**: `corporate_actions` held no splits until the O7 backfill, so the factor was 1.0 — the prerequisite that makes a backtest trustworthy is what armed the bug. Three defences now: `schwab_prices.start_date_for` clamps every pull at the symbol's latest split ex-date (so Schwab can only write bars on the current basis), `ingest/fmp_history.py --repair-split-basis` re-sources restated sessions from the raw FMP endpoint, and `jobs/price_basis_check.py` fails the day a stored series does not step by a split's ratio. A raw series JUMPS at an ex-date; an adjusted one does not, and that arithmetic is the only evidence either way.
- **A BASIS VIOLATION NAMES ITS KIND, and one of the two kinds is unrepairable (D57).** `pre_adjusted` — the series does not step at all — is Schwab's case and is fixed by re-sourcing. `ratio_mismatch` — it stepped by the WRONG amount — means the action log and the bars disagree about what the event WAS, and since FMP's raw feed is its adjusted feed with that log reversed out, both of its series carry the error. The old message asserted the first cause for both and would have sent an operator to `--repair-split-basis` to re-fetch the same bad numbers. **A mis-logged era is REFUSED, not reconstructed**: inferring the true ratio from the observed step uses the price to fix the price, and it is not identifiable anyway when a stock dividend and a cash dividend go ex on the same date. `price_basis_breaks` (migration 022) records `(symbol, break_date, logged_ratio, observed_step, reason)` and `features.technical.load_bars` drops the earlier bars — the one chokepoint the lab, `backtest.engine` and `backtest.regime` already share — applied BEFORE the lookback is cut, so a refused symbol gets a SHORT frame rather than a long one padded with unjoinable bars, and a date wholly inside the era returns NOTHING so every downstream reading abstains. **A recorded break is a KNOWN STATE, not a failure**, like a preflight SKIP: the check fails only on unrecorded violations and prints the recorded ones into `job_runs.details`, so what is quarantined is read rather than remembered. Today the only break is WY 2010-07-20.
- `expirationType` has FOUR values: S=standard monthly (third Friday, what D22 means), W=weekly, Q=quarter-end, M=MONTH-END. `M` is a trap: it is not "monthly." Filter on S (startswith is fine), with third-Friday heuristic as fallback; both agreed on all 23 live expirations.
- `extrinsicValue` is **unusable by construction — it returns distance-from-the-money, not extrinsic value.** Diagnosed 2026-10-20 on a live SPY chain: a Jan-2027 put at strike 50 with spot 771.38 is marked 0.01 with `timeValue` 0.01 and reports `extrinsicValue` 721.39, i.e. `spot - strike` to the cent. 5,247 of 8,214 contracts disagree with `timeValue` (63.9%), and 4,113 report a value larger than their own mark, which is arithmetically impossible. It agrees on ITM contracts, so an ATM spot check misses it entirely. Use `timeValue` for extrinsic, always. Keep the regression test that pins `timeValue` and the fixture carrying the wrong `extrinsicValue` so a future switch to the better-named field fails.
- Refuse chains with `isChainTruncated` or `isDelayed` (a truncated surface stored whole is a permanent undetectable lie). Exclude `nonStandard`/mini contracts.
- IV arrives as percent → convert to decimal at the boundary. `-999.0` sentinel → NULL. ATM = nearest strike, not delta-0.50. `interpolate_iv30` never extrapolates past the curve ends. `expirationDate` is an ISO string, not epoch ms.
- Auth: `client_from_token_file`, never `easy_client` (hangs headless). Access token 30 min, refresh token 7 days, then full re-auth (manual copy-paste flow; the port-less `https://127.0.0.1` callback cannot bind a local server, and schwab-py's `client_from_manual_flow` is the settled mechanism). Live IV can print absurd values (seen 2473%) on 0-DTE/far strikes; the D22 filter already excludes them, no clamp.

## Schema conventions (all previously verified against live PG16 + Timescale 2.29)
- Dual time keying on every time-series table: `ts TIMESTAMPTZ` (UTC, hypertable dimension) + `session_date DATE` (ET trading day, the join key).
- Compression policies staggered (chains 14d, estimates 90d, iv 180d, prices 365d), each delay longer than any backfill window. **No retention policies anywhere**, locked by `test_no_retention_policies`.
- `job_runs` with `is_critical`; `v_day_status` view derives `day_complete` by query (orchestrator reads the view, never a hard-coded job list). Partial unique index: one `running` row per job per day. `job_run` closes from `finally` catching BaseException; `clear_stale_runs()` for kill -9.
- `daily_candidates` is relational, not a hypertable (N rows a day), and takes UPDATEs — it is deliberately NOT one of the four append-only history tables. Its forward-return columns are filled with `COALESCE` so a value is written once and never rewritten, and it carries NO foreign key on `symbol` for the same reason `shadow_book` has none: it records what the engine SAW on a date, and a universe rebuild must not be able to delete the evidence.
- `tickers` rows deactivate (`is_active=false` + `deactivated_on`), never delete. `UNIQUE NULLS NOT DISTINCT` on `events` and `positions`. `fundamentals.raw JSONB` escape hatch. TEXT + CHECK instead of native ENUMs. `news_articles` PK `(source_provider, article_id, symbol)`.
- A dividend writes to BOTH `events` (radar) and `corporate_actions` (adjustment log), with a round-trip test proving the parser and `features/adjustment.py` agree.

## Conventions
- Python 3.11+, `requirements.txt` + `requirements-dev.txt` split, `psycopg[binary]` v3, pydantic v2, `requests` + `tenacity` (no provider SDKs for FMP/Finnhub), `schwab-py`, pandas/numpy.
- ruff: py311, line 100, rules E/W/F/I/UP/B/C4/SIM/RET/PTH/DTZ/T20/ARG/RUF. DTZ is deliberate (bans naive datetimes). T20 waived for jobs/, scripts/, ingest/, db/init.py.
- Never commit secrets. `.gitignore` blocks `.env*` (except `.env.example`), `*token*.json`, `data/*`. `.env.example` documents every variable (FMP_API_KEY, FINNHUB_API_KEY, SCHWAB_APP_KEY, SCHWAB_APP_SECRET, SCHWAB_CALLBACK_URL=https://127.0.0.1, SCHWAB_TOKEN_PATH=data/schwab_token.json, DB vars incl. separate admin creds, SMTP + ALERT_EMAIL_ONFAIL, TELEGRAM_BOT_TOKEN + TELEGRAM_CHAT_ID).
- **`.env.example` IS A CONTRACT THE DEPLOY CHECKS (`scripts/env_contract.py`), under ONE REQUIREDNESS RULE: a variable is REQUIRED only if the engine cannot run its required pipeline without it.** Everything else is optional — either the feature it belongs to is OFF when it is blank (email, Telegram, S3 upload, EDGAR, token sync) or it has a CODE-SIDE DEFAULT that takes over — and both are states the engine is designed to run in, so neither may fail a deploy. In practice the rule reads straight off `core/settings.py`: required means the accessor calls `require()`, and a named test enforces that direction (the converse does not hold — the email accessors all `require()` while email is optional, because nothing calls them when the channel is off). It is checked against the FILE, not the ambient environment, because `settings` loads `.env` with `override=False` and cron has almost none of the shell's variables. The marker is `# [OPTIONAL: <feature>] <reason>` and exempts a variable from being set AND from the placeholder check, since for something optional those are the same state and every reader already treats a placeholder as absent (`settings.looks_like_placeholder`). **The FEATURE NAME is not decoration**: the deploy groups what is off by feature, because the operator's question is never "which variables are blank" but "what is switched off on this box" — and a placeholder in a REQUIRED variable stays a deploy failure. The rule was adopted after two deploys failed on variables the VM never uses (`ENGINE_PATH`, a laptop setting, and a half-marked SMTP block); case-by-case marking is what let both through. 11 of 48 variables are required.
- **The commit-message status line is GENERATED, never typed: `python scripts/test_counts.py`.** It runs the unit suite, the integration suite against `ie_test`, and ruff, then prints "N unit + M integration tests pass; ruff clean on F files" — and refuses to emit anything if any of the three fails, because a line claiming a green suite above a commit where it is not reads as verification. `--append <file>` writes it into a commit message; `--no-integration` says so IN the line rather than dropping the clause. It exists because the same number was typed from memory twice and was wrong both times: a number typed by hand twice is a process, not a slip.
- Idempotent ingestion (re-running a day upserts, never duplicates). Rate limiter is a sliding window, not a token bucket, shared via core. `for_each_symbol` fails a job above 25% symbol-failure rate with a 10-symbol minimum sample; total failure always raises regardless of sample size (never "ok, 0 rows" when everything failed).
- Scoring logic unit-testable with fixture DataFrames, no network. Integration tests only under `pytest -m integration`.
- Prefer boring, explicit code. This runs unattended.
