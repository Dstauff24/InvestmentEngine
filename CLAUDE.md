# CLAUDE.md — Investment Decision Engine (Rebuild, Oct 2026)

## What this is
A personal investment decision-support engine for a Schwab brokerage account (swings, long holds, options). It ingests quant + qual data, scores tickers through a 4-pillar confluence model, surfaces complete trade plans (entry/stop/TP1/TP2/R:R/size) in two tiers, tracks every idea in a Shadow Book, and sends a daily email digest. **The human makes every final decision.** Phase 1 = the brain, no UI.

**Context:** this repo is a REBUILD. A prior build completed all 7 scaffold steps (411 tests, live-validated against Schwab and FMP) and was lost when an unpushed Codespace auto-deleted on 2026-10-20. Nothing here is speculative: every convention and finding below was implemented and verified once already. `docs/REBUILD_KICKOFF.md` is the work order; `docs/engine-decisions-and-todo.md` is the authoritative decision log (D1–D39).

## Non-negotiable process rule (D30)
**Commit and push to GitHub at the end of every working session, and after every completed step. No exceptions.** The repo on GitHub is the system of record; a Codespace is disposable. Never report a step complete without naming the commit that was pushed.

**Deploying is `./scripts/deploy.sh` on the engine host** — pull, dependencies, `db.init` (migrations then schema), config validation, then the orchestrator's own `--dry-run` preflight. It makes NO provider calls and writes no market data (no `ALLOW_LIVE_CALLS` anywhere in it, pinned by a test): a deploy that ingested would merge "did the deploy work" with "did tonight's data arrive", which have different answers and different fixes. Exit code is the hard-error count; a preflight SKIP is a known state, not a failure. The one-time deep-history catch-up is a separate, ordered runbook in README.md — actions BEFORE bars, basis repair after, `price_basis_check` to prove it.

## Locked decisions that constrain code (full detail in the decision log)
- **Data sources:** Schwab Trader API (prices, option chains, positions, via `schwab-py`), Financial Modeling Prep on `/stable/` (fundamentals, estimates, calendars; currently FREE tier, see free-tier mode below), Finnhub free tier (news), SEC EDGAR + FRED (free), Claude API (transcript tone scoring, Phase 2).
- **Universe (D14):** S&P 500 + Nasdaq 100 constituents, avg 20-day volume >1M, active options chain, plus `config/watchlist.txt`. ~500 names. While FMP constituents endpoints are plan-gated, the universe builds from `config/constituents_static.txt` (manually sourced, dated header) with a logged warning.
- **Cadence (D15):** daily bars only in Phase 1. Jobs run post-close (~4:30 PM ET) on trading days. Host TZ = America/New_York for cron; DB stores UTC.
- **Snapshots (D7/D22):** every trading day, store option chains (strikes within ±15% of spot, nearest 4 MONTHLY expirations, per-ticker aggregate IV) and FMP analyst estimates (when the plan allows). **These histories cannot be bought back. Snapshot jobs are is_critical and must never silently fail.**
- **Database (D20):** Postgres (≥15, for UNIQUE NULLS NOT DISTINCT) + TimescaleDB. Hypertables: `prices_daily`, `option_chain_snapshots`, `estimate_snapshots`, `iv_daily`. Relational: `tickers`, `fundamentals`, `corporate_actions`, `events`, `news_articles`, `ideas`, `shadow_book`, `positions`, `alerts`, `job_runs`, `schema_migrations`.
- **Prices (D24):** `prices_daily` is append-only raw OHLCV. No stored adjusted columns. `corporate_actions` is the immutable source of truth; `features/adjustment.py` computes factors at read time with an `as_of` date, in two modes: `split_only` (technical structure) and `total_return` (performance, backtests, dividend-adjusted stops).
- **Append-only enforcement:** a static test fails on any DELETE (or ON CONFLICT DO NOTHING) against `prices_daily`, `option_chain_snapshots`, `estimate_snapshots`, `iv_daily`. Writers use ON CONFLICT DO UPDATE.
- **Scoring (D2, reweighted by D32):** Technical 40 / Fundamental 30 / Catalyst 20 / Sentiment 10 → composite 0–100. Weights live in `config/scoring.yaml`, never hard-coded. D32 demoted Sentiment (free-tier news is the thinnest input) and gave the weight to Fundamental ahead of the revision signal; the conflict veto still lets a demoted Sentiment cap an idea, so demotion is not disabling.
- **Ranking (D33):** an absolute score decides nothing. Ideas rank by composite percentile within the universe; the digest surfaces at most `ranking.max_ideas_per_day` by rank. Ranking selects among ideas that already cleared a D12 gate — it never promotes one that failed.
- **Tier A diversity (D34):** agreeing pillars must include Technical plus at least one of Fundamental or Catalyst. Technical + Sentiment is one signal measured twice.
- **Vehicle (D36):** IV rank picks the vehicle on every Tier A idea and is printed on the card — buy optionality below `iv_vehicle_low`, shares in the middle, defined-risk premium selling above `iv_vehicle_high`. Needs the self-built IV rank (D7/D22).
- **Sizing (D37/D38):** adds only once the stop is at breakeven, with total risk capped at the original allocation — initial risk never rises. Max 2 concurrent swings per sector; the third surfaces watch-only.
- **Allocation (D35):** two sleeves with separate scoreboards — Core 65% (ETFs + holds, benchmarked to its blend) and Growth 35% (swings + options + tactical cash, benchmarked to SPY total return). Quarterly one-way ratchet sweeps half of any excess above 3 points into Core permanently; drawdowns are never replenished mid-quarter.
- **Abstention semantics (D41):** a pillar with insufficient data ABSTAINS; the composite is computed over SCORING pillars with weights RENORMALIZED (never scored 50 — that invents evidence). An abstainer can neither agree nor conflict, so D12's counts bind on scored pillars (**a two-pillar idea reaches at most Tier B**) and the conflict cap applies only to scored pillars. **Technical must have scored or there is no idea** — it carries 40 points and is never genuinely unavailable for a liquid listed name, so its absence means the data is wrong. The abstention mask is printed on every card and recorded on every Shadow Book row (`scored_pillars`, `pillars_scored`), because 72 from four pillars and 72 from two are different claims and the number cannot say which; D39 groups calibration on it.
- **The mapping (`scoring/pillars.py`):** one shape everywhere — `50 + 50 × clamp(x / full_credit, −1, +1)`, neutral at 50, SATURATING at ±full_credit so one wild sub-signal cannot dominate a pillar. A pillar is the MEAN of the sub-signals that scored, i.e. D41's renormalization one level down. **Equal sub-weights within a pillar is a decision, not a missing parameter**: D2/D32 state the weights between pillars; nothing states whether revision momentum outranks margin trend, so a number there would be false precision. ATR is deliberately unscored (a risk unit, not an opinion). Beyond its horizon a catalyst scores `None`, not 0 — no news is not bad news.
- **Two phases (`scoring/runner.py`):** phase one scores every symbol, phase two ranks percentiles and tiers. Forced by D33 — a percentile cannot be known until every symbol is scored. Sector composites are built ONCE per run and cached (11 builds, 422 hits on the live 433-symbol universe).
- **"Surfaced" (D42):** an idea is surfaced when it clears a tier gate AND ranks within `max_ideas_per_day`. ONLY surfaced ideas become Shadow Book calls; the rest roll into one `daily_scoring_stats` row (tier counts, mask histogram, composite distribution, and the GATES IN FORCE so a later change cannot reinterpret it). On 2026-10-21, 190 qualified and 5 surfaced — tracking all 190 would make the Shadow Book a record of coverage rather than judgement. The aggregate is the paper-phase evidence for tuning gates (D39(3)) and deliberately cannot say whether a different cut would have made money.
- **Recipes read features, not scores.** `scoring/recipes/` re-measures nothing: every level a plan hangs on was computed once in `features/`. Passing pillar scores in would let a mapping-scale change silently move a recipe's trigger. **R:R is DERIVED from structure, never configured** — "TP2 = 3R" would make R:R a constant and D12's R:R gates satisfied by construction on every idea. R:R is quoted to TP2 (D11's "true win"), not TP1.
- **Existence-gating vs outcome thresholds (D43):** a parameter deciding whether a recipe FIRES AT ALL (`range_contraction_ratio`, `min_base_weeks`, the RSI band) can never accrue Shadow Book evidence while set too tight — an unfired recipe produces no closed ideas — so D39's 30-idea rule is unsatisfiable for it BY CONSTRUCTION. These are swept in the step 10 backtest, with the LIVE MEASURED DISTRIBUTION setting the sweep range. Outcome-dependent thresholds (tier gates, pillar weights, sizing) stay D39-governed: only what happened to the ideas they admitted can judge them.
- **Sizing and books (D44):** sizes resolve against `SHADOW_ACCOUNT_VALUE` from `.env`, and shadow/paper ALWAYS use the virtual account even once Schwab balance sync exists — otherwise the Shadow Book's history would depend on deposits having nothing to do with the strategy. **The sector guard (D38), heat cap (D17) and max-concurrent-swings count open positions WITHIN ONE LADDER STATE ONLY.** Each of SHADOW/PAPER/LIVE keeps its own book: `decision/book.py` reads open `shadow_book` rows for shadow/paper and `positions` for live. Without the scoping a shadow idea would block a live one, which is backwards.
- **Cards render complete on thin data.** `decision/idea_builder.py` prints every section or says why it cannot: "vehicle: shares (IV rank unavailable, day 0 of 60 — D7 history still accumulating)" is the honest output of a young engine, where a blank line or a bare "shares" would both be worse. Sizing uses `entry_high` (worst fill) while R:R is quoted at the zone midpoint — sizing off the midpoint would let a top-of-zone fill exceed D17's budget.
- **Idea gating (D12):** Tier A = ≥3 pillars agree AND composite ≥70, min R:R 2:1. Tier B = compelling asymmetry, 2 pillars or composite 55–69, min R:R 3:1, reduced size.
- **Risk (D17/D18):** Tier A 2.5% of account per trade; Tier B 0.75%/idea with hybrid monthly budget (4% base at entry, 50% of realized Tier B gains replenish, 6% ceiling, calendar month); max 6 concurrent swings; total open heat ≤10% (active trades only; holds/ETFs excluded, they run on thesis triggers with no hard stops); options defined-risk only, 5%/mo realized-loss budget, 3% max per position; circuit breaker (2 losing weeks or −5% month → Tier B paused, Tier A halved until a winning week). Buckets: ETF 35 / holds 30 / swings 20 / options 10 / cash 5; risk-off (SPY<200MA + VIX>25) → swings 10, options 5, cash 20+. Single name ≤10%, sector ≤30%. All in `config/risk.yaml`.
- **Dividends (D19):** total-return measurement everywhere; dividend-adjusted stops; no new swing long within 2 days of ex-date; flag short-call assignment risk when extrinsic (use `timeValue`) < dividend × buffer; dividend cut = thesis-review trigger; ETF DRIP on, hold dividends → cash bucket.
- **Shadow Book (D13):** every surfaced idea (Tier A, Tier B, and discretionary) logged with projections at time of call, tracked to outcome whether or not taken. `shadow_book.symbol` has NO FK to `tickers` (discretionary ideas may be off-universe). North-star metric = expectancy per recipe and tier.
- **Projections are frozen; the enforced stop is not.** `shadow_book` carries `proj_stop` (what we said at the call, never written again) beside `current_stop` (what the tracker enforces, moved to breakeven at TP1 per the trim rules, lowered by a dividend per D19(2)). A projection that drifted toward the outcome would measure nothing, which is the entire point of D13.
- **The ambiguous bar resolves PESSIMISTICALLY.** Daily bars carry no intrabar sequence, so a bar touching both stop and target is unresolvable — and the cost is asymmetric: assuming the target came first flatters every result in exactly the case where a real trade was most likely stopped out. `shadow_book/outcome_tracker.py` books the stop, unless the stop is already at breakeven, where TP1 was already paid. `last_evaluated_on` is what makes the daily job safe to re-run.
- **The backtest and the Shadow Book share ONE fill implementation.** `backtest/resolve.py` builds the call dict and hands it to `shadow_book.outcome_tracker.evaluate_call`; it re-decides nothing. The entry-zone fill, the pessimistic ambiguous bar, the breakeven move at TP1 and the D19(2) dividend stop are modelling CHOICES, and a backtest that scored them differently would report an expectancy the Shadow Book could never reproduce — two numbers disagreeing for ever with no way to say which was the strategy.
- **What a backtest here can and cannot measure (D39(4)/O7).** It measures the RECIPES. It does not measure the composite, the tier gates or D33's ranking: the fundamental statements reach back five years but the estimate-revision, IV-rank, insider and news series all start 2026-10-21, so a historical composite would be a two-pillar number dressed as a four-pillar one. **No portfolio queue** — every signal is taken, because D17's heat cap and D38's sector guard would measure which signal arrived when a slot was free rather than what the recipe is worth. **One open trade per symbol per recipe**, or a setup that persists for a week counts its single outcome five times. **Survivorship is unfixable here**: the universe is today's constituents, so every delisted loser is absent and every number is an upper bound.
- **Next-day entry, and friction is charged (D39(4)).** A plan is formed on the close of the bar that produced it, so the first bar it can trade against is the next one — filling on the signal bar is the most common way a backtest invents an edge. `backtest/costs.py` charges slippage adversely on both sides and reports gross and net R side by side, because a strategy whose edge disappears into the spread never had one. The option overlay is modelled and UNEXERCISED: D36 picks the vehicle from IV rank, whose history starts 2026-10-21.
- **Expectancy, not hit rate (D13).** 35% at +3R beats 70% at +0.5R, and a report led by hit rate ranks them backwards. Every population prints its own n and flags itself under D39(2)'s 30-closed-trade floor. **A backtest cannot promote anything** — D40 counts closed SHADOW BOOK ideas, and a simulated trade is not one.
- **A threshold whose measurement is bounded by itself cannot set its own sweep range (D43).** `_detect_base` only finds consolidations that already fit `max_base_depth_pct`, so the measured depth distribution can only ever propose a tighter cap; `min_base_weeks` is bounded from below the same way. Those two are swept around the shipped value with the circularity stated. The gates whose quantity is measured independently (`range_contraction_ratio`, break volume, RSI, gap) get their range from the live distribution, as D43 intends.
- **Benchmarks are priced and nothing else (D17/D35/D39).** `tickers.is_benchmark` (migration 012) carries SPY: out of `v_active_universe` so nothing scores or surfaces it, `passes_liquidity=false` so it cannot enter a sector composite, spared by `deactivate_absent` because it is in no constituents pull, and unioned in by `ingest/schwab_prices.py` alone. Without it "SPY below its 200-day MA" had no series to read — the D14 universe is index constituents and contains no index.
- **Regime is stamped at call time, never derived later (D45).** `shadow_book.regime_at_call` (migration 013) carries `<trend>_<volatility>` from D17's SPY-vs-200MA test plus SPY realised-vol terciles, computed by `backtest/regime.py` — the SAME code the backtest tags trades with, so a live call and a simulated one land in the same cell. Deriving it at read time would be wrong for the same reason `gates_in_force` travels with a call: the benchmark series gets revised (a late print, a split backfill, a repaired basis), and a recomputed regime would move old calls between cells underneath a promotion decision already made. `unknown` before the benchmark has 200 sessions — a regime nobody can compute is not a regime. **D40's ladder is evaluated per recipe x REGIME**, so a strategy can be LIVE in one regime and SHADOW in another and D39(2)'s 30-idea floor applies per cell.
- **How a "beat" is established is a MODE, not a number (O12/D47).** `recipes.post_earnings_drift.beat_source` is `growth_proxy` (year-over-year EPS growth, what the recipe had to use while stored earnings rows carried no actuals) or `verified` (`CatalystFeatures.surprise`: reported actual against consensus estimate). They answer different questions — a company can grow 20% year on year and still miss the quarter the drift premise rests on. `verified` refuses when either number is missing, because `None` is "cannot establish" and never "no beat". The surprise divides by `abs(estimate)` so a loss-maker beating a negative estimate scores positive. Untagged by `[OPEN]` (it is not a number) and pinned by a named test; it moves only on a decision, with both backtested side by side first.
- **`base_breakout` is DORMANT by decision (O13), not by accident.** `enabled: false`, because a recipe firing zero times because of a parameter looks identical in the logs to one that is switched off and only one of those is a decision. The cause is a measurement defect: `base_contraction` is `mean(high-low) over the last fifth of the base / mean over the whole base`, a statistic centred on 1.00 BY CONSTRUCTION (measured p10 0.81, median 1.00, p90 1.23 over 8,236 observations), so the 0.6 gate asks for something that barely occurs and the loader rightly refuses anything >= 1.0. Redesign `_detect_base` before any re-sweep; re-tuning the ratio against the current detector is tuning against a broken yardstick.
- **Alerts (D16, amended Oct 21 2026):** daily email digest, Tier A and Tier B clearly separated, PLUS Telegram as the page channel. `alerts/notify.py` fans out to whatever is configured; `alerts/telegram.py` and `alerts/mailer.py` never raise, sit behind the D27 gate, refuse under pytest, and write one `alerts` row per channel with a namespaced dedupe key. Telegram's token travels in the URL (redact it everywhere) and 4096 chars is a hard limit Telegram rejects rather than truncates (split on line boundaries).
- **Network consent (D27):** `core/netguard.py`. No live network call without `ALLOW_LIVE_CALLS=1` on the invocation (CLI/cron, never `.env`). Inside pytest the answer is always no, flag or not. The gate sits ahead of the rate limiter and transport in every client. A blocked call is a failed job step, never a silent zero-row success.
- **Exits:** per-strategy shape enforced by the loader. `swing` has `max_holding_days` (45, [OPEN]); `option` times out at expiration (`max_holding_days` must be null); `hold` exits on thesis triggers only (null). A day-count on options or holds is a hard config error.
- **Promotion ladder (D40):** every recipe carries a status — `shadow` (surfaced, tracked, FLAGGED NOT ACTIONABLE), `paper` (also sized against a virtual account with the full D17/D18 stack), `live` (the human trades it). New strategies always enter `shadow`, backtest or no backtest. SHADOW→PAPER needs ≥30 closed ideas with positive expectancy; PAPER→LIVE needs sustained expectancy plus calibration within tolerance; demotion is automatic. Thresholds are `[OPEN]` in `scoring.promotion`, and the loader rejects a ladder that contradicts itself. `shadow_book.status_at_call` stamps every idea — expectancy mixed across a boundary averages two different strategies and makes the rule circular.
- **STANDING CONVENTION for every `features/` module: insufficient data returns `None` — never a number, never `False`.** The scoring layer owns the meaning of abstention. A 200-day MA from 40 bars, a YoY growth rate against a quarter that does not exist, or `stacked=False` because the slow MA is unknown are all plausible-looking wrong answers that propagate into a composite with nothing to flag them. "We cannot see X" and "X is absent" are different claims.
- **Evidence depth (`features/evidence.py`):** any feature computed from a series the ENGINE accumulates — IV history (D7/D22), estimate snapshots — reports an `EvidenceDepth` beside its value: distinct observations AND calendar span, which differ (ten snapshots in a week ≠ ten over a year). Without it, the Shadow Book cannot record how much evidence an idea stood on, and D39's calibration work could never ask whether thin evidence predicts unreliability. Two kinds of thin, deliberately not collapsed: **mathematically undefined** (an IV rank needs a high and a low, so `features/iv.py` gates hard on `iv_rank_min_history_days` and records `iv_daily.history_days`), versus **correct but noisy** (a consensus moving 2.00 → 2.39 across two snapshots moved exactly that much, so revision momentum reports the value and lets depth carry the uncertainty). Never fold depth into the value — a feature that quietly shrank its own number on thin evidence would be making a scoring decision.
- **SEC EDGAR (D39, Pillar C):** access is CONDITIONAL on a descriptive User-Agent carrying a real contact address and on staying under ~10 req/s. `core/settings` REFUSES the `.env.example` placeholder (sending `you@example.com` satisfies the format while giving them no way to reach us — the anonymous traffic the rule exists to stop), the limiter uses a **one-second** window with 5 slots (a per-minute window would allow all its slots inside one second, breaking the only limit the SEC states), a 403 is never retried, and the D27 gate plus a day budget apply as to any provider. An unconfigured UA is an expected SKIP in preflight, not a failure.
- **EDGAR's `primaryDocument` is the RENDERED HTML, not the data.** A submissions feed points at `xslF345X06/form4.xml`, which is an XSL-transformed page served with an `.xml` extension; the machine-readable XML is `form4.xml` in the same folder. `raw_xml_document()` strips any leading `xsl*/` segment (the directory is versioned — X03, X05, X06). Verified live 2026-10-21: every Form 4 failed with "mismatched tag: line 29" until the prefix was stripped, and the error points nowhere near the cause.
- **Validated live 2026-10-21 (AAPL + MSFT, 26 rows):** filing lag ran **0-4 calendar days, mean 2.96** — the legal rule is two BUSINESS days, which crosses a weekend into four calendar days. And **not one row was an open-market purchase**: 15 sales, 8 option exercises, 3 tax-withholding. A naive "insider activity" signal would have read 11 compensation events as activity, including $2.1M of `F` (shares withheld for tax) as if it were conviction. The code filter is not pedantry.
- **Point-in-time on FILINGS, not fiscal periods.** `load_fundamentals` keyed `as_of` on `fiscal_date_ending`, so a run standing on April 5 read a quarter that would not be filed until April 30 — a lookahead whose only symptom is a backtest that looks better than the strategy. Keyed on `COALESCE(filing_date, accepted_date::date)` now, and a row with neither is EXCLUDED rather than dated by an invented reporting lag. Same rule as Form 4s below. Live runs were unaffected in practice, which is exactly why it stayed invisible until a backtest asked for a date in the past.
- **POINT-IN-TIME HONESTY on Form 4s:** a filing is knowledge when the SEC ACCEPTS it, up to two business days after the trade. `insider_transactions` stores `filed_at` (NOT NULL) and `transaction_date`, and **every read and backtest keys on `filed_at`** — keying on the transaction would let a backtest act on a purchase before anyone could know, invisibly, because the results merely look better. `filed_at` is NOT NULL so a row that cannot be read point-in-time cannot be stored.
- **Insider clusters are config, not code (D25/D39):** N distinct insiders, a D-day window, a dollar floor. **DISTINCT insiders** — one director filing four times is one opinion reported four times. **Transaction code `P` only**: `A` is an award, `M` an option exercise, `F` tax withholding, and counting those measures a compensation schedule rather than an opinion. Derivatives are excluded and the loader refuses a config that tries to include them. Rows are stored UNFILTERED so the rule can change without re-fetching EDGAR.
- **Pillar A inputs (`features/technical.py`):** split-only adjusted prices (D24), newest bar LAST (a descending frame is refused, not measured backwards), and **insufficient history returns None, never a number** — a 200-day MA from 40 bars is a plausible-looking wrong answer that propagates into a composite undetectably. RSI is Wilder's, because the recipe's 40-50 band was written against what a charting package shows. Relative volume excludes today from its own baseline. Relative strength vs sector (D33) is a return DIFFERENCE, not a ratio, which is unstable exactly in the quiet-sector case that matters most.
- **Pillar D measures CHANGE, not level (D32):** the readings are a tone DELTA (trailing window vs a longer, non-overlapping baseline) and a news-VOLUME spike against the symbol's OWN normal flow. A permanently gloomy stock is not a sell signal every day. Absolute tone is an input to those, never a signal alone.
- **The tone scorer is swappable and its identity is recorded.** `ToneScorer` is the whole interface (`name`, `version`, `score`); `LexiconScorer` is Phase 1 and the Claude API scorer is Phase 2. Every reading carries `scorer_id` ("name/version") and `news_articles.sentiment_scorer` persists it, because the two are differently calibrated instruments and averaging their readings measures neither — D39's calibration curve would be computed on a series that silently changed definition. Versioned because a reworded lexicon is a different instrument. An unknown scorer name RAISES rather than defaulting. An unscoreable text returns `None`, not 0: "no opinion" and "neutral" differ, and a pile of zeros drags every delta toward nothing.
- **"No news" is not "we weren't looking".** Any rate computed over a window must be bounded by `news_coverage_start()` — the day the ENGINE began collecting, which is global, not per symbol. Found live: JNJ reported a 7.4x volume spike purely because a 23-day baseline divided 30 articles by 23 days when the series reached back two of them. Below full coverage the spike abstains.
- **[OPEN] parameters (D25):** every number no decision fixes lives in config tagged `# [OPEN]`, with a row in `docs/open-parameters.md` and a sync test. Changing a decision-fixed value without a decision fails a named test.

- **The estimate-revision clock started 2026-10-21.** First `analyst-estimates` snapshot stored that day. No history exists before it and none can be bought. D32's Fundamental weight of 30 rides on a series that is still shallow.
- Budget `fmp.daily_call_budget` = **9000**, limiter `FMP_RATE_LIMIT_PER_MIN` = **600** (Premium allows 750). The budget's job changed: not "stay inside the allowance" but "stop a runaway loop before it makes 200,000 calls". Keep it.

- **Quote endpoints are SPLIT and the split is silent.** One symbol: `/stable/quote?symbol=X`. Many: `/stable/batch-quote?symbols=A,B` — note the PLURAL parameter; `symbol` there is a 400. Passing a comma list to `/stable/quote` returns HTTP 200 and `[]`. The free tier 402'd that same request, which hid the bug for the whole free-tier period. `quotes()` raises on a wholly empty batch.
- **A 402 does NOT prove a plan gate.** `/stable/ratios?symbol=BRK.B` 402s while `?symbol=AAPL` 200s, and an unknown symbol returns 200 + `[]`. `_optional` therefore confirms with a known-good canary symbol before marking an endpoint unavailable — inferring a gate from one symbol's 402 would NULL the valuation columns for every remaining symbol under a log line naming the wrong cause.
- Retained fallbacks (a plan can lapse; billing can 402 an endpoint overnight): `config/constituents_static.txt` stays maintained and tested; `fmp_fundamentals` keeps degrade-on-402 with gaps in `job_runs.unavailable_endpoints`; `fmp_estimates` keeps the probe that sets its own `is_critical`.
- `scripts/fmp_probe.py` probes BOTH API generations across every endpoint the client calls and distinguishes 402 (plan) from 404 (path). Re-run after any plan change.

## Validated API findings (do not rediscover these)
**FMP `/stable/`:** quote at `/stable/quote?symbol=X`; `calendarYear` is now `fiscalYear` (accept both); fundamentals cost 5 calls/symbol, refreshed on staleness (>7 days or reported since), not schedule; estimates must drop already-reported periods before diffing.
- **The EOD `full` endpoint is SPLIT-ADJUSTED, and the RAW one is named as though it were the opposite.** `/stable/historical-price-eod/full` returns a `close` already adjusted for every later split — verified 2026-10-21, LRCX's 10-for-1 on 2024-10-03 shows no price jump at all. Raw bars (what D24 stores) are on `/stable/historical-price-eod/non-split-adjusted`, whose fields are `adjOpen`/`adjHigh`/`adjLow`/`adjClose` with **no `close` key**, and those `adj*` values are the UNADJUSTED prices. Trusting the field names gets it backwards in both directions. Volume on the `full` endpoint is split-adjusted too, which is harmless for a 20-day average and wrong for anything stored.
- **EVERY CALENDAR ENDPOINT IS CAPPED AT 4,000 ROWS AND TRUNCATES SILENTLY.** Measured 2026-10-21: a 7-day window returned 1,823 rows, and both a 14-day and a 30-day window returned exactly 4,000 — covering an arbitrary slice of the days requested (the 30-day ask came back as 11 days from the MIDDLE). Over the 190-day window the events job uses, `earnings-calendar` returned the last 48 days and dropped every past earnings date: 76 rows for 433 symbols, none in the past. That, not `events.backward_days`, is why `post_earnings_drift` could not fire and `pullback_to_trend` refused every symbol for an unverifiable earnings exclusion. The radar now reads **`/stable/earnings?symbol=X`, one call per symbol, no cap** (`refresh_symbol_earnings`, 433 calls/day — the cost is the point), and `FMPClient._calendar` raises `FMPTruncatedResponse` on any response at the cap. A 90-day calendar window also 402s while a 30-day one answers, so a 402 there means "window too wide", not "plan".
- The per-symbol earnings payload uses `epsActual`/`revenueActual` where the calendar uses `eps`/`revenue`. Two parsers, deliberately: reading one shape with the other's names yields rows that parse cleanly and carry nothing.
**Schwab (schwab-py 1.5.x, live-validated 2026-09-03):**
- **SCHWAB'S DAILY CANDLES ARE SPLIT-ADJUSTED, so it RESTATES its own history.** Verified 2026-10-21: all 14 splits inside the stored window showed no price jump in Schwab's bars, BKNG's 25-for-1 included. D24 defines `prices_daily` as raw and applies split factors at READ time, so a stored Schwab bar from before a split gets adjusted twice. **It was dormant**: `corporate_actions` held no splits until the O7 backfill, so the factor was 1.0 — the prerequisite that makes a backtest trustworthy is what armed the bug. Three defences now: `schwab_prices.start_date_for` clamps every pull at the symbol's latest split ex-date (so Schwab can only write bars on the current basis), `ingest/fmp_history.py --repair-split-basis` re-sources restated sessions from the raw FMP endpoint, and `jobs/price_basis_check.py` fails the day a stored series does not step by a split's ratio. A raw series JUMPS at an ex-date; an adjusted one does not, and that arithmetic is the only evidence either way.
- `expirationType` has FOUR values: S=standard monthly (third Friday, what D22 means), W=weekly, Q=quarter-end, M=MONTH-END. `M` is a trap: it is not "monthly." Filter on S (startswith is fine), with third-Friday heuristic as fallback; both agreed on all 23 live expirations.
- `extrinsicValue` is **unusable by construction — it returns distance-from-the-money, not extrinsic value.** Diagnosed 2026-10-20 on a live SPY chain: a Jan-2027 put at strike 50 with spot 771.38 is marked 0.01 with `timeValue` 0.01 and reports `extrinsicValue` 721.39, i.e. `spot - strike` to the cent. 5,247 of 8,214 contracts disagree with `timeValue` (63.9%), and 4,113 report a value larger than their own mark, which is arithmetically impossible. It agrees on ITM contracts, so an ATM spot check misses it entirely. Use `timeValue` for extrinsic, always. Keep the regression test that pins `timeValue` and the fixture carrying the wrong `extrinsicValue` so a future switch to the better-named field fails.
- Refuse chains with `isChainTruncated` or `isDelayed` (a truncated surface stored whole is a permanent undetectable lie). Exclude `nonStandard`/mini contracts.
- IV arrives as percent → convert to decimal at the boundary. `-999.0` sentinel → NULL. ATM = nearest strike, not delta-0.50. `interpolate_iv30` never extrapolates past the curve ends. `expirationDate` is an ISO string, not epoch ms.
- Auth: `client_from_token_file`, never `easy_client` (hangs headless). Access token 30 min, refresh token 7 days, then full re-auth (manual copy-paste flow; the port-less `https://127.0.0.1` callback cannot bind a local server, and schwab-py's `client_from_manual_flow` is the settled mechanism). Redact `code=`/`session=`/tokens from all error output; clamp HTTP loggers to WARNING during auth. Throttle to ~100/min (limit 120). Live IV can print absurd values (seen 2473%) on 0-DTE/far strikes; the D22 filter already excludes them, no clamp.
- Sanity relationships that validated the whole pipeline once and should again: SPY IV30 below single names, SPY 25d skew positive vs ~0 for MSFT, SPY put/call OI far above single names.
- `schwab_chains` writes `tickers.has_options` true/false from whether a chain returned; that arms the D14 options gate (which abstains on None).

## Schema conventions (all previously verified against live PG16 + Timescale 2.29)
- Dual time keying on every time-series table: `ts TIMESTAMPTZ` (UTC, hypertable dimension) + `session_date DATE` (ET trading day, the join key).
- Compression policies staggered (chains 14d, estimates 90d, iv 180d, prices 365d), each delay longer than any backfill window. **No retention policies anywhere**, locked by `test_no_retention_policies`.
- `job_runs` with `is_critical`; `v_day_status` view derives `day_complete` by query (orchestrator reads the view, never a hard-coded job list). Partial unique index: one `running` row per job per day. `job_run` closes from `finally` catching BaseException; `clear_stale_runs()` for kill -9.
- `tickers` rows deactivate (`is_active=false` + `deactivated_on`), never delete. `UNIQUE NULLS NOT DISTINCT` on `events` and `positions`. `fundamentals.raw JSONB` escape hatch. TEXT + CHECK instead of native ENUMs. `news_articles` PK `(source_provider, article_id, symbol)`.
- A dividend writes to BOTH `events` (radar) and `corporate_actions` (adjustment log), with a round-trip test proving the parser and `features/adjustment.py` agree.

## Conventions
- Python 3.11+, `requirements.txt` + `requirements-dev.txt` split, `psycopg[binary]` v3, pydantic v2, `requests` + `tenacity` (no provider SDKs for FMP/Finnhub), `schwab-py`, pandas/numpy.
- ruff: py311, line 100, rules E/W/F/I/UP/B/C4/SIM/RET/PTH/DTZ/T20/ARG/RUF. DTZ is deliberate (bans naive datetimes). T20 waived for jobs/, scripts/, ingest/, db/init.py.
- Never commit secrets. `.gitignore` blocks `.env*` (except `.env.example`), `*token*.json`, `data/*`. `.env.example` documents every variable (FMP_API_KEY, FINNHUB_API_KEY, SCHWAB_APP_KEY, SCHWAB_APP_SECRET, SCHWAB_CALLBACK_URL=https://127.0.0.1, SCHWAB_TOKEN_PATH=data/schwab_token.json, DB vars incl. separate admin creds, SMTP + ALERT_EMAIL_ONFAIL, TELEGRAM_BOT_TOKEN + TELEGRAM_CHAT_ID).
- Idempotent ingestion (re-running a day upserts, never duplicates). Rate limiter is a sliding window, not a token bucket, shared via core. `for_each_symbol` fails a job above 25% symbol-failure rate with a 10-symbol minimum sample; total failure always raises regardless of sample size (never "ok, 0 rows" when everything failed).
- Scoring logic unit-testable with fixture DataFrames, no network. Integration tests only under `pytest -m integration`.
- Prefer boring, explicit code. This runs unattended.
